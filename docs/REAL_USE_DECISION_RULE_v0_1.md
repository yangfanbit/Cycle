> 目的：把「怎么算有效」在看到结果**之前**定死，杜绝事后挑口径、挑阈值、挑样本。
>
> 本文件全文的 sha256 前 16 位已固化在

## 1 · 观察设计（单人 N-of-1，不用 ABAB）

| 项 | 冻结值 |
|---|---|
| 使用场景 | 工作台默认页（当前主题挖掘 / 前瞻排程）产生的「是否值得继续研究」判断 |
| 触发方式 | **事件驱动**：出现 `LEAD` / `CONFIRM` / `REJECT` / `NO_LEAD` / `BLOCKED` / `UI_FRICTION` 任一即记一条；不按日历补记 |
| 观察单位 | **cluster**（同一题材 / 事件 / 同一周的高度相关线索共用一个 `cluster_id`）；条目数只报规模，不作样本量 |
| 观察期 | 自第 1 条记录起 **2–8 周**，到期即收口，不无限延长 |
| 对照形式 | **多基线 / 交替处理**：以「用工作台的研究」与「惯常方法的研究」按 cluster 交替记录；**不做 ABAB 撤回**——研究判断一旦产生就不可「撤回不知情」，强行撤回会引入 carry-over |
| 单条成本上限 | **2 分钟内填完**；超限即记为 `UI_FRICTION`，不补写细节 |

★ 正向 / 负向 / 零触发 / 使用摩擦**同等记录**。缺任何一类，整份日志标 `BIASED_SAMPLE`，不下结论。

## 2 · 主指标与判定阈值（事前固定，不事后调）

| # | 指标 | 计算口径 | 通过阈值 |
|---|---|---|---|
| 1 | **新线索率** | 经事后核实为「新的、可核的历史对应」的 cluster 数 / 已结算 cluster 数 | ≥ 0.20，且至少 **3 个独立 cluster** 各自有一条可核对应 |
| 2 | **研究耗时变化** | 同一研究问题下，用工作台的净耗时 − 惯常方法净耗时；按 cluster 取中位数 | 中位数 ≤ −0.5 小时（即省半小时以上）；**只报差值与分布，不设显著性检验** |
| 3 | **事后可核性** | 工作台给出的每条对照带原始 URL / 日期 / 可复核理由的比例 | ≥ 0.80；「口径不清」计入不可核 |

三项**全部**达到阈值才判 `INCREMENT_SUPPORTED`；任一不达标判 `NOT_SUPPORTED`；
数据不足判 `INSUFFICIENT_SAMPLE`。`NOT_SUPPORTED` 是合法结论，不是失败。

辅助记录（必须与主指标同等认真）：**负向缺口**（惯常方法找到而工作台没有的对应）、
**覆盖边界**（因数据不足无法研究的问题）。缺这两项 → `BIASED_SAMPLE`。

## 3 · 样本量门槛（防小样本讲故事）

| 状态 | 条件 | 允许输出 |
|---|---|---|
| `NO_RECORDS` | 0 条 | 只输出「本轮未开展」，**不得**写有效性结论 |
| `INSUFFICIENT_SAMPLE` | 已结算 cluster < 20 | 只输出触发量、耗时分布、数据限制与摩擦；**不得**输出任何比例、分数、判定 |
| `ELIGIBLE` | 已结算 cluster ≥ 20 且四类记录齐全 | 才允许按 §2 判定 |

★ 参考已核实的公开做法：Anamnesis 在 20 条已结算预测以下不出校准结论，
并明确写出「此时检验对 30% 偏差的检出率很低」；Brier / 比例类统计在几十条上主要是噪声。
本项目**不输出概率分数**（宪法禁止），但沿用「<20 不下结论」这条纪律。

## 4 · 防回填 / 首次判断才计分

- **T 时刻冻结**：`question` / `verdict_at_T` 由本人在看到后续行情或结果之前写下；
  `frozen_at`、`data_as_of`、`artifact_ref` 由系统自动生成，不接受手填。
- **正文不可改**：更正一律新建 `amend-NN`，不覆盖原记录；`saveRecord` 对已存在的 `record_id` 直接返回。
- **事后分离**：`posthoc_check` 独立存储、独立导出数组，写它不会改动正文。
- **首次判断才计分**：同一 `record_id` 若有多条事后核对，**只取 `checked_at` 最早的一条**
  计入 §2 的分子；后续修订单列 `REVISION`，标「学习记录，不计入 headline」。
  这条是防止「证据到齐后补写判断」污染分数。
- **不得回填**：`frozen_at` 必须早于该记录的首条 `checked_at`；倒序或同秒视为可疑，标 `SUSPECT_TIMING`。
- **不得编造**：没有记录就写「本轮未开展」；「没有触发」≠「工具无效」≠「成功」。

## 5 · 合规度（防止只记顺手的）

| 指标 | 冻结值 |
|---|---|
| 合规度定义 | 观察期内**实际产生记录的天数** / **实际使用工作台的天数** |
| 目标 | ≥ 0.70 |
| 判定有偏 | < 0.50 → `BIASED_SAMPLE`，只报摩擦不下结论 |

★ 单人场景无法靠第三方点名督促，因此**使用天数**由工作台本地记录（导出 JSON 的
`frozen_at` 去重日期）与本人自报的使用天数共同给出；两者不一致时以较小值为分母，
宁可低估不夸大。

## 6 · 明确禁止（宪法边界，不因本轮解锁）

- 用 5/10/20 日板块超额、行情涨跌、命中率、胜率作为有效性证据；
- 把「线索」写成推荐、买卖点、选股清单，或给龙头 / 弹性标签；
- 把内部评估视图的 `priority_score` 当作验收指标（它只是生成对照材料的启发式排序）；
- 用「功能还不够 / 数据还不够」为理由，在结论为 `INSUFFICIENT_SAMPLE` 时启动新一轮开发。

## 7 · 收口动作

1. 导出工作台 JSON 到 `.tmp/real_use/records/`（不入库）；
2. 跑 `check_real_use_protocol_v0_1.py --check`，把输出的**状态标签**原样抄进
   `docs/PROJECT_STATE.md`，不改写、不美化；
3. 状态为 `INSUFFICIENT_SAMPLE` / `NO_RECORDS` 时，报告只写触发量与数据限制；
4. 状态为 `ELIGIBLE` 时才按 §2 给出 `INCREMENT_SUPPORTED` 或 `NOT_SUPPORTED`，
   并附负向缺口与覆盖边界。
