## 二、★★ 一项协议层阻塞：**Campaign 粒度未定义**

这是本轮审查**最重要的发现**，它决定 4 条 DEFER 的命运。

**实测既有对象的时间跨度**：

```
C-2019-COMM-5G      2019-06-06 → 2022-10-11   （3.4 年 · 8 个 lifecycle 阶段）
C-2020-POWER-NE     2020-09-22 → 2022-12-30   （2.3 年 · MAIN_RISE/PEAK/RETRACEMENT/SECONDARY/DECLINING）
C-2021-POWER-GREEN  2021-09-07 → **OPEN**     （开放式 · 按项目约定回退至 2025-12-31）
```

**后果**：本包 5 条候选**全部落在既有对象的时间范围内**：

```
COMM-002    ⊂ C-2019-COMM-5G
POWEREQ-001 ⊂ C-2020-POWER-NE
POWEREQ-002 ⊂ C-2020-POWER-NE
POWEROP-001 ⊂ C-2021-POWER-GREEN
POWEROP-002 ⊂ C-2021-POWER-GREEN
```

**为什么不能自动否决**：规则 4「**同一时间 ≠ 同一个 Campaign**」—— 时间重叠本身不构成重复。

**真正的问题**：

> 若采用**「机制段」**粒度（本包的做法），则**既有对象也应拆分**
> （如把 `C-2020-POWER-NE` 拆为 2020 平价段 / 2021 双碳段 / 2022 出口段）——
> 那是**对冻结区的修订**，属独立轮次。
> 若保持**「长周期」**粒度，则本包的子段**不应独立成 Campaign**。

★ 粒度标准在库内**本身不统一**（见 SF-b）：`C-2019-COMM-5G` 是长周期（8 阶段），
而 `C-2021-POWER-GREEN` 只有单阶段 `MAIN_RISE`。

→ **须用户裁定**。ThreeC Agent 不单方面改粒度（类比协议 §3.4）。

## ★★ 勘误（2026-10-13，写库当轮）

### 勘误 1：SF-a 的诊断**错误**（我误判了）

**原文（§八）**写：「既有对象在 export 中 `securities` 为**空数组**，但 DB 里有登记
→ **export 未填充该关联**，导致产品侧无法展示标的。」

**这是错的。** 实测：

```
export 顶层有**扁平的 `securities` 数组**（含 campaign_id 关联），完整填充：
  C-2019-COMM-5G → 5 条（烽火通信 600498 / 中兴通讯 000063 / 天孚通信 300394 /
                        新易盛 300502 / 中际旭创 300308），含 name / ticker / role
campaign 对象里的字段是 `security_ids`（id 列表），**不是** `securities`
产品侧实测（探针）：
  C-2019-COMM-5G → [{"name":"烽火通信","ticker":"600498","role":"leader"}, …] ✓ 完全正确
```

**误判根因**：我用 `c.get('securities')` 读 campaign 对象 —— 该字段**不存在**，
`undefined or []` 得到空数组 → **我把「字段不存在」当成了「数据缺失」**。

★ 教训（与「结构校验只查形状」同族）：**查之前先确认字段名**；
「取到空」不等于「没有」。**字段名错误会伪装成数据缺失。**

★ 实际状态：**产品侧一直正常** —— `formalCampaignToTimeline` 取的是正确字段
（`s.name` / `s.ticker` / `s.role`），UI 也**已在渲染**「代表股票」
（`CampaignDetail.tsx`）。用户 2026-10-12 的诉求（主题详情含龙头）**已部分满足**。

★ 唯一真实的小瑕疵在 **legacy 路径**：`verifiedCampaignToTimeline`（`timelineAdapter.ts`）
用 `name: cs.security_id` 把内部 ID 当公司名 —— 但该路径消费的是
`data/candidate/` 的硬编码数据（`AGENTS.md` §5.1 明确 `data/` **无消费者**），
**产品不走它**。已记录，未改（避免动 legacy 冻结面）。
