## 2. 发现：3 处 Runbook 缺口

### 缺口 1（**已修**）· 观察必须关联对象，否则时间线永远为空

原 Runbook 步骤 4 只说「写观察」，**没说要填 `linked_object_id`**。
而 Lifecycle Tracking 完全依赖它 —— 不填，对象的生命周期**永远是空的**。

→ **已修**：步骤 4 补上「关联研究对象」小节 + 说明为什么重要 + L1/L3 的作用。

### 缺口 2（**待定**）· 观察输入文件与 revision 的版本关系未定义

**本次实际踩到**：`observations/2026-10.json` 是**输入文件**。若为了加新观察而**就地追加**，
就会让**已签发的 `MS-2026-10-06-02` 失去可复现性**（用同一份输入重跑会得到不同的快照）。

→ **本次临时处理**：新建 `observations/2026-10-r2.json`（原 5 条**逐字未改**，只追加 2 条），
并用 `--supersedes` 归档 `02`。

→ **待定**：正式约定应是哪一种？
- **A · 按 revision 分文件**（本次做法）：`2026-10.json` / `2026-10-r2.json` …… 直观但文件渐多
- **B · 按 snapshot_id 命名**：`MS-2026-10-06-02.json` …… 一一对应，最无歧义
- **C · 月度一份、revision 用 `--snapshot-id` 区分**：最省事，**但放弃早期 revision 的可复现性**

**我倾向 B** —— 输入与产物一一对应，`--check` 才有意义。

### 缺口 3（**待定**）· Runbook 步骤 5 的命令不覆盖「修订」场景

现有命令示例只给了**首次装配**。而实践中只要改动 `market_regime` / `observations` / 研究对象，
就必须走**新 revision**（`CANONICAL` 不可变），需要额外传 `--snapshot-id` 与 `--supersedes`。

→ **待定**：把「修订流程」写进 Runbook（含「何时需要新 revision」的判定规则）。

## 3. 演练同时确认「有效」的部分

| 机制 | 实战表现 |
|---|---|
| **CANONICAL 门禁** | 生效；未签发内容默认不展示 |
| **`CANONICAL` 不可变 → 新 revision** | 生效；`02 → 03` 走通，`02` 自动 `ARCHIVED` + `superseded_by` |
| **append-only（L3）** | 生效；原 5 条观察**逐字未改**即通过 |
| **PIT 安全** | 生效；`asOf` 早于观察所在快照时看不到它们 |
| **diff 月度对照** | 生效；正确显示「观察 +2」而非被同日 revision 挤掉 |
| **索引自动重建** | 生效；4 份快照状态一致 |
